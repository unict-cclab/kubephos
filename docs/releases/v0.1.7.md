# KubePhos v0.1.7

## Independent application deployments

The new **Deployments** section installs catalog applications without starting an
experiment. Choose a ready cluster, name and namespace, then use the same
Application parameters, initial replicas, resources, topology and Istio settings
as experiment configurations.

For a multi cluster group, a complete copy is installed on every member in the
same namespace. Cilium groups keep Istio disabled. Details show member progress,
saved settings and Activity logs. Applications remain installed until removed;
cleanup uses the recorded lifecycle and namespace ownership checks, including
after partially completed multi cluster installations.

Namespaces must be new. An active experiment reserves its namespace throughout
initialization, manual waiting, execution and cleanup. Independent deployments
reserve their namespaces until removal succeeds. Database guards also reject
conflicting concurrent requests. Owners and administrators can view and remove
deployments, and users can target only assigned clusters.

## Workload and interface

- Configure sinusoidal workloads with **Minimum** and **Maximum (req/s)** instead
  of baseline and amplitude. Minimum must be nonnegative and maximum must exceed
  minimum. Validation covers the form and backend; previews, saved settings and
  the Locust generator use the same bounds. Existing baseline/amplitude profiles
  retain their curve until their range is edited.
- Show the running backend version at the bottom of the sidebar, including when
  the sidebar is collapsed. Official builds display their release tag; development
  builds display `dev`.

## Upgrade

Back up the installation and wait for active work to finish. Set
`KUBEPHOS_VERSION=v0.1.7` in the installation `.env`, then run `./update.sh` from
the v0.1.7 archive or checkout. Add `--directory /path/to/installation` for a custom
installation path. If using a temporary local image, first restore
`KUBEPHOS_IMAGE=ghcr.io/unict-cclab/kubephos`.

Migration 054 runs automatically. Existing configurations, suites, experiments and
credentials are retained. State transfer requires matching migration schemas;
imported independent deployments are assigned to the importing administrator.
